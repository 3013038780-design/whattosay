# WhatToSay 微信小程序需求文档

版本：v0.2 · 更新日期：2026-10-16

状态：需求整理稿；尚未开发、上线或完成全部语料精读。

本文作为产品需求的主文档。与早期方案冲突时，以本文为准。标为“用户明确”的内容来自用户要求；标为“建议”的内容是待体验验证的产品设计，不视为用户已经确认每一个细节。

## 1. 产品背景与目标【用户明确】

用户经常参加饭局，突然被邀请起身敬酒或讲两句时容易词穷，担心表达不合场面。希望开发一个可向大家开放、可分享传播的微信小程序，快速提供符合当下场景的祝酒词。

产品不仅要缓解尴尬，还应帮助使用者说得有文采、有文化积累，既能照顾中国饭局中的人情分寸，又能让听者感到内容有出处、有意味。不能把“快速可用”简化为普通祝福句，也不能以泛泛的模型生成替代用户提供的文化资料。

核心目标：

1. 临时被点到时，迅速获得可以直接说出口的祝酒词。
2. 根据场景、人物关系与说话身份，给出得体的表达。
3. 内容有文采、节奏感与文化底蕴，朗朗上口，便于现场表达。
4. 以用户提供的七份 PDF 为主要内容依据，理解诗歌、历史与酒场文化后再组织内容。
5. 支持随机推荐、英文、诗歌、日期、季节与二十四节气。
6. 支持分享小程序与内容，让其他人也能使用。

## 2. 内容方向的修正【用户明确】

此前方案过于偏重“自然短句”和自主原创，没有充分体现用户提供语料的目的。本次明确调整：

- 文化资料是内容工作的基础，不能仅作为装饰或书名清单。
- 默认输出应兼具文采与可说性，适当运用典故、诗词、对偶、排比、回环等表达方法。
- 简短不等于浅白；有文采不等于生僻堆砌；押韵不应牺牲意思和人情分寸。
- 用户希望“听起来有知识积累”，因此既要提供好句，也要让使用者能理解其中的典故和用意。
- 原创、改编与原文引用须明确区分。未经资料检索与审核的临时生成，不进入默认推荐池。
- 英文作为风格选项保留，不能替代中文文化内容的主线。

## 3. 目标用户与使用情境

### 3.1 核心用户【用户明确】

参加饭局、聚会和社交活动时，需要临时敬酒或表达祝福的人。产品面向公众使用，具备便于好友、群内传播的分享能力。

### 3.2 核心情境【用户明确】

- 被突然叫起来敬酒，头脑空白，不知如何开口。
- 有领导在场，需要表达尊重并适当点到领导。
- 年轻朋友聚会，可以更活泼、好玩。
- 男女社交、认识新朋友或相亲，需要另外一种有分寸的表达。
- 希望借当天日期、季节或节气找到一个自然又有文化意味的切入点。
- 看到好的祝酒词，希望发给朋友或群，让大家一起使用。

“小朋友们的局”暂按年轻朋友聚会理解；若指儿童聚会，需要用户进一步澄清。

## 4. 场景与关系模型

### 4.1 初始场景

| 场景 | 需求来源 | 表达目标 | 关键分寸 |
| --- | --- | --- | --- |
| 领导、职场饭局 | 用户明确 | 尊重、感谢、得体，适度体现文化修养 | 区分领导在场与单独敬领导；不越过主宾，不遗漏全桌 |
| 年轻朋友小聚 | 用户明确 | 轻松、风趣、朗朗上口 | 笑点与典故适合熟悉程度，不把所有内容写成网络段子 |
| 男女社交、初次相识 | 用户明确 | 破冰、认识、留下好印象 | 不能仅因异性同桌就默认追求或亲密关系 |
| 相亲、约会 | 用户明确 | 温雅、轻松、有余地 | 区分初见和熟悉，不贸然许诺或制造压力 |
| 家人、长辈 | 建议纳入第一版 | 亲切、感恩、祝福 | 祝寿与普通家宴不同，重视称呼和辈分 |
| 同学、老友重逢 | 建议扩展 | 怀旧、知己、珍惜相聚 | 不编造相识年数，不无故转成伤逝 |
| 接风、送别、庆功、生日、婚宴、答谢 | 资料支持的扩展 | 按事件选用表达结构 | 主人、客人和被祝福者的话不能互换 |

### 4.2 匹配维度【建议】

不能只选“饭局类型”就结束匹配。内容组织应支持以下条件，但界面渐进展开，不要求救急用户逐项填完：

- 我是谁：普通参与者、主人、来宾、下属、同辈、晚辈、活动代表。
- 我要敬谁：全桌、领导、长辈、朋友、初识对象、主人、特定主角。
- 谁在场：领导、客户、长辈、同事、新朋友、混合关系。
- 关系程度：初见、认识不深、熟悉、知己。
- 为何相聚：普通聚会、感谢、庆功、送别、祝寿等。
- 当前环节：开席、席间轮到我、回敬、结束。
- 氛围与长度：庄重、温雅、豪爽、诙谐；一句、短段、完整段。
- 可选事实：姓名/职务、真实感谢事项、真实共同经历。

匹配优先级建议：场景与人物分寸 → 表达目的 → 文化内容与风格 → 时令 → 随机变化。不得为押韵、应景或使用名句而破坏场景适用性。

## 5. 功能需求

### FR-01 救急入口【用户明确目标；交互为建议】

首页设置明显的救急入口。默认无需登录、无需填写个人资料，即可看到一条经过审核、具有文采的通用祝酒词。用户可快速选择场景再换取更贴合的内容。

验收：初次使用不被注册、长问卷或 AI 等待阻塞；通用句同样需经过内容审核。

### FR-02 场景与对象选择【用户明确】

支持领导职场、朋友小聚、男女社交/初识、相亲等场景。敬全桌与敬某个人分别处理；允许不清楚对方姓名或职务时使用得体泛称。

验收：同样选择“领导在场”，敬全桌和单独敬领导得到不同结构的内容。下属不会自动使用领导的团队号召口吻。签约、开工、客户答谢、颁奖等活动分别匹配；迎宾区分主人与客人，送行区分辞职、调任、退休、毕业与出国学习，开业区分试营业、乔迁、改制及正式开张；普通来宾不得自动代表主办机构，或作出奖惩、投产、政策等承诺。

### FR-03 随机推荐与换一句【用户明确】

在适合当前条件的已审核内容中随机推荐，不从全部内容中盲抽。支持换一句；在候选池允许时，本场尽量不重复。

验收：换一句不改变用户已选择的场景；候选不足时优先放宽时令偏好，不突破人物关系条件。老同学、战友等重逢默认以共同关系为主，不因有人担任领导就自动改成职场奉承；涉及往事和玩笑时，还需顾及配偶、新朋友及其他听众是否知情。池耗尽时有明确提示或轮换策略。

### FR-04 文采、韵律与长短版本【用户明确质量；选项为建议】

默认版本应体现文化底蕴。建议提供“典雅有出处”“诗词入酒”“诙谐助兴”“英文举杯”等选项，并提供一句版、短段版和完整段版。

可使用四字节奏、对偶、排比、层递、借景入情、典故转意；不要求每条全用，也不要求全部硬押韵。缩短版本必须保留表达主旨或文化亮点，不能退化为固定的万能祝福。一段围绕清晰主旨与主要意象展开，避免堆叠互不相连的比喻；同一条内容同时检查口头节奏与人物语气。

验收：每条正式内容需现场朗读审核；断句清楚，主语一致，称呼、时段、年份和活动阶段相互吻合，收尾可直接落到祝福与举杯动作。具体风格名称和长度范围在体验后确定。

### FR-05 诗词、典故与出处【用户明确文化方向；展示方式为建议】

结果正文之外，提供可折叠的“这一句有来头”：出处、作者/作品、原意、在本场合的用意。救急时无需先读解释，想了解时能够展开。

- 原文引用保持字句准确，显示引用身份。
- 化用须标明“化用”，不能冒充作者原话。
- 根据资料重新组织的祝酒词须标明整理/改编性质。
- 存疑的作者、故事、字句不得标成已核实史实。
- 文化资料与典故来源建立可追踪记录。

验收：每条文化内容可追溯到书名、PDF 页码和具体章节/条目；古诗引用同时记录原作，不仅记录现代书籍。

### FR-06 英文内容【用户明确】

支持英文祝酒词。建议中英对照、短句优先，并保留原来的祝福目的。中文典故如无法自然译出，应提供适合英文语境的表达与说明，不硬译成难以理解的句子。

英文内容须独立检查语法、习惯表达与中文释义，资料中的英文不因已经出版便视为合格。

英文朗读为后续建议，不是第一版必需依赖。

### FR-07 每月 1—31 号【用户明确】

按日号提供不同主题与推荐内容；每个日期可以有多条、多个场景版本。允许查看其他日期。

验收：实际月份不存在的日期不被推荐为“今天”；主题不强求数字谐音。同一天可按场景产生不同的合适推荐。

### FR-08 四季与二十四节气【用户明确】

按实际日期推荐四季、二十四节气内容，结合诗词、习俗与意象组织表达。时间基准采用北京时间；日历计算与文案分开维护。

验收：区分节气当日与节气期间；不将节气写成每年同一公历日；不凭日期虚构实际天气、地点或窗外景色。清明等时令按相聚目的选取内容，不能仅因日历命中就套用庆功语气。

### FR-09 分享整个小程序【用户明确，第一版必需】

支持用户主动分享给微信好友或微信群。对方点击后可直接使用，不要求知道 GitHub 或自行安装工程。

验收：不同微信账号可通过分享卡片进入首页；分享封面与标题能说明产品用途。

### FR-10 分享当前内容与场景【建议实现用户的分享目标】

结果页可分享当前精选祝酒词，接收者先看到相同内容，再继续生成自己的版本。支持直接进入指定场景。

验收：分享后不重新随机导致内容变样；稳定内容 ID 和版本可恢复；失效内容有说明和可继续使用的入口。私人的称呼或经历不默认进入公开分享。

朋友圈适配、祝福海报与小程序码列为后续增强项，需真机与账号环境验证。

### FR-11 收藏与现场阅读【建议】

支持收藏、最近使用、大字展示和便于记忆的分行。基础收藏先存在用户本机；不将本地保存误称为云端同步。

### FR-12 回敬、收尾与以茶代酒【建议】

支持接住别人的祝福、结束自己的讲话、用茶或饮料表达敬意。保留与核心祝酒词相同的文化质量要求。

### FR-13 趣味玩法【用户允许拓展；具体玩法为建议】

可探索数字主题、抽词成句、诗词接句或轻量文字酒令。与救急入口分开，不影响快速找词。用户所说的“敬酒令”主要意图是生成祝酒表达；是否同时开发完整游戏模块，暂不视为已确定需求。

## 6. 文化语料建设要求【本次核心】

### 6.1 资料范围

用户提供七份 PDF；经 SHA-256 核验，两份《中国品酒诗话》字节完全一致，实际为六部不同著作。书目和本轮阅读记录见 [语料阅读记录](corpus-study.md)。

### 6.2 阅读与整理流程

1. 逐部盘点目录、版本、页码和文本可提取程度。
2. 阅读与具体场景相关的完整章节，扫描正文先 OCR，再对照原页校对。
3. 提取诗词、典故、祝酒结构、人物关系与场景分寸，建立条目。
4. 区分原文、作者解释、民间传说、OCR 结果与编者整理。
5. 核对古诗字句、作者、篇名及典故原意；有分歧则记录并暂缓发布。
6. 针对对象与场景整理可说的祝酒词，并保留资料关联。
7. 做文化正确性、场景得体性和现场朗读三类审核。
8. 通过后进入推荐池；用户反馈用于修订内容和标签。

完整阅读与审核是一项单独工作，不能以“已提取整本文字”代替“已读懂”，也不能以 OCR 成功代替校对完成。

### 6.3 必需内容字段【建议的数据设计】

| 字段组 | 内容 |
| --- | --- |
| 身份与场合 | 场景、说话人身份、对象、在场人物、熟悉程度、目的、席间环节 |
| 文化依据 | 书目 ID、PDF 页、书内页、章节/条目、原作作者与篇名、原意、事实可信状态 |
| 祝酒表达 | 正文、断句、风格、长短版本、适用条件、不适用条件、结尾方式 |
| 内容性质 | 原文引用 / 化用 / 依据资料整理 / 独立原创，引用与整理部分分别记录 |
| 时令与语言 | 日期主题、季节、节气、语言、译文 |
| 维护与分享 | 稳定 ID、版本、审核状态、审核备注、可分享状态 |

### 6.4 内容来源原则

默认采用“资料检索 → 场景匹配 → 已审核整理内容”。如后续使用模型，模型应基于明确检索到的文化材料辅助整理或改写，并保留依据。找不到合适依据时优先返回已有审核内容，不能编出一个典故补位。

此前仓库的自主原创短句只作为早期交互示意，不代表正式内容标准，不进入默认推荐池。

## 7. 内容质量与验收

正式发布的每条内容都必须通过以下检查：

1. **有依据**：文化内容能追溯；引用、化用、整理身份准确。
2. **懂原意**：不因字面吉利就忽略原诗的送别、哀悼、讽刺或失意语境。
3. **合身份**：说话人有资格表达这句话，不替别人承诺，不冒充活动代表。
4. **合关系**：对初识、领导、长辈、知己使用不同分寸。
5. **有文采**：具有贴切意象、文化意味或有效修辞，避免整批套用同一祝福。
6. **能朗读**：句式有呼吸点，生僻字可提供注音，典故可解释，结尾自然收住。
7. **不虚构**：不编造相识年数、指导经历、成就、家事或现场天气。
8. **可选择**：不将劝饮、罚饮或酒量比较作为默认社交任务。

建议评分：文化贴切、文采、节奏、场景分寸、可说性五项各 1—5 分；每项至少 4 分才进入试用池。此为拟定内容门槛，需用户试读校准。出处错误、身份错位或事实虚构直接退回，不以平均分抵消。

必须覆盖的测试情境：领导在场但敬全桌；晚辈敬长辈；主人欢迎客人；客人感谢主人；老友相聚；初次相亲；送别与庆功；节气当日；数字不易谐音的日期；接收者从分享进入。

## 8. 使用体验与技术约束【建议】

- 微信原生小程序作为当前推荐技术路线，不代表产品仅给个人使用。
- 本地基础审核内容确保核心出句不依赖后端；首次打开仍需微信加载代码包。
- 模型生成不阻塞救急，云端失败有已审核内容兜底。
- 小屏、字体放大、英文换行与大字展示可读。
- 预置内容加载后，点击换句到渲染完成目标不超过 300ms；是待真机验证的目标。
- API 密钥只在服务端，输入、请求量、超时和费用应可控。
- 只收集功能必要的信息；无需为了救急要求手机号、联系人或定位。
- 公众上线需要实际微信账号、AppID、开发权限及后台要求的发布材料；GitHub 同步不等于微信发布。

## 9. 第一版与后续范围

### 第一版优先

语料整理与文化内容审核；救急入口；核心场景与对象；有文化依据的推荐与换句；诗意与英文；日期、季节和节气；好友/群分享；精选短句分享落地；收藏与大字展示。

第一版可先覆盖有限但质量可靠的内容池，不能用未经审核的大量文本填充“文化感”。尚无证据支持明确工期或句库规模，本轮不承诺数量。

### 后续增强建议

回敬与收尾；海报和朋友圈适配；英文朗读；更丰富的事件场景；基于资料的定制改写；跨设备收藏；多人同桌不撞词；文字酒令玩法。

## 10. 已确定与待校准
